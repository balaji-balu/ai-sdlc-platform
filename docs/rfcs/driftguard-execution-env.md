1. Executive Summary
Long-running autonomous code-generation agents require the ability to edit files, install dependencies, run compilers, and execute test suites. Granting an un-trusted, potentially drifting LLM agent direct access to a developer's host operating system poses severe security and stability risks.
This RFC proposes a virtualized, ephemeral execution sandbox abstraction layer. It ensures that all file mutations and command executions occur inside a strictly bounded, isolated container. This design also gives DriftGuards a clean, unpolluted environment to observe changes and capture system-level telemetry.

2. Sandbox Boundary Architecture
The framework decouples the host machine from the agent workspace using an isolated Workspace Provider. For Phase 1, this will leverage a lightweight container runtime interface (CRI), with fallbacks for local mock drivers.

3. Core Interface & Security Contract
Every sandbox driver must implement a strict execution and file manipulation contract. This allows developers to swap between a Local Docker provider, a Wasm-based runner, or a Remote micro-VM provider (e.g., Fly.io / AWS Firecracker) without changing core framework logic.
export interface ExecutionResult {
  exitCode: number;
  stdout: string;
  stderr: string;
  durationMs: number;
  mutatedFiles: string[]; // List of files touched during this execution
}

export interface SandboxVolumeInfo {
  hostPath: string;
  guestPath: string;
  readOnly: boolean;
}

export interface SandboxProvider {
  readonly id: string;
  readonly type: 'docker' | 'firecracker' | 'local-mock';

  /** Boots up the ephemeral secure environment */
  initialize(volumes: SandboxVolumeInfo[]): Promise<void>;

  /** Safely writes code or configurations generated by the agent */
  writeFile(relativePath: string, content: string): Promise<void>;

  /** Reads workspace state for Observer analysis */
  readFile(relativePath: string): Promise<string>;

  /** Executes terminal commands (e.g. `npm test`, `cargo build`) securely */
  executeCommand(command: string, timeoutMs: number): Promise<ExecutionResult>;

  /** Tears down and completely wipes the workspace state to prevent pollution */
  destroy(): Promise<void>;
}



4. Sandbox Telemetry Hook for Drift Verification
To enable Phase 1 DriftGuards (specifically Layer 5: Implementation Drift and Layer 6: Deployment Drift), the sandbox acts as an observation deck.
When a command runs inside the container, the sandbox hooks into standard output/error and tracking loops:
Dependency Modification Detection: If the agent runs an install command (pip install, npm install), the sandbox intercepts the event and flags it for the Layer 7 (Maintenance) Guard to verify if dependencies drifted from pinned versions.
Execution Timeouts: If an agent accidentally generates an infinite loop runtime bug, the sandbox strictly enforces timeoutMs thresholds, reporting an EXECUTION_HALTED event back to the Core Orchestrator event bus instead of hanging indefinitely.

5. Architectural Tensions & Open Questions
We invite community systems engineers to evaluate and propose optimizations for:
File Sync Synchronization Latency: When an agent edits 40 files across a complex repository structure, how do we track and optimize file system change notification speeds back to the Observe engine loop?
Network Isolation: Should the execution container have full outbound internet access? (Required for downloading packages via npm/pip, but risks an agent leaking proprietary codebase tokens via malicious network calls if it drifts or gets injected with a bad payload).
Pre-warmed Sandboxes vs Boot Overhead: Compiling environments (like Rust or heavy Java runtimes) takes a long time to spin up from scratch in an ephemeral environment. How do we balance perfect clean-slate isolation with fast continuous loop execution?
